/speckit-plan

Create the technical implementation plan for the bulk email dry-run campaign feature using the following architecture and constraints.

## Technology Stack

* Runtime: Node.js with TypeScript.
* Backend framework: NestJS.
* Database: PostgreSQL.
* ORM and migrations: Prisma.
* Queue: BullMQ with Redis.
* Queue observability: Bull Board mounted inside the NestJS API.
* Email transport: Nodemailer using pooled SMTP connections.
* Dry-run SMTP target: Mailpit.
* Frontend: static HTML, CSS, and vanilla JavaScript.
* Local orchestration: one `compose.yaml` compatible with both Docker Compose and Podman Compose providers.

Implementation details must remain traceable to the approved constitution and feature specification.

## Application Structure

Use one NestJS codebase containing:

* HTTP API;
* campaign orchestration and reconciliation;
* BullMQ job producers;
* BullMQ delivery workers;
* SMTP transport;
* persisted campaign progress queries;
* static frontend serving;
* read-only Bull Board integration;
* health and readiness endpoints.

Serve the static frontend from the NestJS application. Do not introduce a separate frontend framework or frontend container.

Organize the application into focused modules, including:

* `CampaignModule`
* `RecipientModule`
* `CampaignPreparationModule`
* `DeliveryModule`
* `QueueModule`
* `MailModule`
* `ProgressModule`
* `HealthModule`
* `BullBoardModule`

Names may be adjusted when the generated design provides a clearer bounded responsibility, but campaign orchestration, delivery, and progress-query responsibilities must remain separated.

## Data Model

### Recipient

`Recipient` is the reusable source dataset and is independent of campaigns.

Required fields:

* `id`
* `email`
* `name`, nullable
* `createdAt`
* `updatedAt`

Recipient records are seeded before campaign creation.

The recipient dataset is not modified through the application during this phase.

### Campaign

`Campaign` represents one submitted mail blast.

Required fields include:

* `id`
* `subject`
* `body`
* `status`
* recipient snapshot upper-bound or equivalent stable snapshot marker
* preparation cursor
* total recipient count
* pending count
* rejected count
* sent count
* failed count
* delivery-unknown count
* total delivery-attempt count
* `startedAt`
* `completedAt`, nullable
* `createdAt`
* `updatedAt`

Campaign statuses must distinguish at least:

* `PREPARING`
* `RUNNING`
* `COMPLETED`
* `COMPLETED_WITH_ISSUES`

An additional campaign-level failure status may be introduced only for an unrecoverable orchestration failure and must not replace recipient-level outcomes.

### CampaignRecipient

`CampaignRecipient` is the durable, per-campaign snapshot and processing record.

There must be one `CampaignRecipient` row for every source recipient included in the campaign snapshot.

Required fields include:

* `id`
* `campaignId`
* `sourceRecipientId`
* snapshot email
* normalized email, nullable when unusable
* snapshot name, nullable
* personalized or fallback name value when needed
* current processing status
* rejection reason, nullable
* delivery failure reason, nullable
* duplicate-of reference, nullable
* delivery attempt count
* queue-enqueue state
* terminal timestamp, nullable
* `createdAt`
* `updatedAt`

The source email and name must be copied into this row so that campaign behavior does not depend on later changes to the reusable `Recipient` record.

Enforce uniqueness for:

* `(campaignId, sourceRecipientId)`;
* the canonical accepted normalized email within a campaign.

Duplicate source rows must still receive their own `CampaignRecipient` records and be marked rejected with `DUPLICATE_EMAIL`.

### DeliveryAttempt

`DeliveryAttempt` records every actual SMTP attempt.

Required fields include:

* `id`
* `campaignRecipientId`
* attempt number
* deterministic queue job identifier
* attempt status
* SMTP response or normalized error information, nullable
* whether delivery acceptance was definitive or uncertain
* `startedAt`
* `finishedAt`, nullable
* `createdAt`

Attempt records are audit history. The current recipient outcome remains on `CampaignRecipient`.

## Campaign Snapshot

When a campaign is accepted, capture a stable upper boundary for the seeded recipient dataset, such as the highest eligible recipient identifier.

Only recipients at or below this boundary belong to the campaign.

Campaign preparation must scan recipients in stable ascending identifier order using keyset pagination:

* query records where `id` is greater than the previous cursor;
* limit the result to a configurable preparation batch size;
* order by the stable unique identifier;
* never use deep `OFFSET` pagination.

Each preparation batch must:

1. copy source recipient data into `CampaignRecipient`;
2. trim and normalize the email address;
3. validate email syntax;
4. record invalid recipients as `REJECTED`;
5. identify later duplicate normalized addresses;
6. record duplicate recipients as `REJECTED`;
7. mark accepted recipients as ready for queueing;
8. persist the preparation cursor before loading another batch.

The complete recipient dataset must never be loaded into application memory.

Campaign preparation must be resumable after API, worker, PostgreSQL-connection, or Redis interruption.

## Single Active Campaign Enforcement

At most one campaign may have an active status.

Active statuses include:

* `PREPARING`
* `RUNNING`

Enforce this invariant inside PostgreSQL using a committed database migration, preferably a partial unique index over active campaign statuses.

The API may perform an initial query to return a friendly conflict response, but correctness must rely on the database constraint.

Concurrent valid campaign submissions must result in:

* one successfully created campaign;
* deterministic `409 Conflict` responses for all losing requests.

The API must translate the database uniqueness violation into the campaign-conflict response.

## Queue Architecture

PostgreSQL is the business system of record.

Redis and BullMQ contain reconstructible operational work. Queue state must not determine the authoritative campaign or recipient outcome.

Use separate logical job types for:

* campaign preparation or preparation reconciliation;
* recipient delivery;
* optional campaign reconciliation or completion checking.

Each accepted `CampaignRecipient` produces one delivery job.

Delivery jobs must be added through bounded BullMQ `addBulk()` calls rather than by constructing the entire campaign job list in memory.

Job payloads must contain identifiers only, such as:

* `campaignId`
* `campaignRecipientId`

Do not put full message bodies, recipient snapshots, or large batches of recipient objects in Redis job payloads.

Use deterministic job IDs derived from the campaign and campaign-recipient identifiers.

A deterministic job ID is an optimization against duplicate queue entries, not the final idempotency guarantee.

The worker must check the persisted `CampaignRecipient` status before starting delivery. A recipient already in a terminal state must produce a successful no-op and must not be submitted to SMTP again.

## Durable Queue Dispatch and Reconciliation

A committed PostgreSQL record must never depend on a single best-effort Redis enqueue call.

Accepted campaign recipients must first be persisted with an enqueue state such as:

* `READY_TO_QUEUE`
* `QUEUED`
* `PROCESSING`
* `TERMINAL`

A dispatcher or reconciliation process must repeatedly:

1. find `READY_TO_QUEUE` records using keyset pagination;
2. add jobs through bounded `addBulk()` operations;
3. update queue-enqueue state;
4. safely repeat the operation after interruption.

The design must handle interruption:

* before BullMQ insertion;
* after BullMQ insertion but before the database state update;
* after a job starts;
* after SMTP communication but before the terminal database update.

Startup reconciliation must detect active campaigns and restore missing preparation, dispatch, or completion work.

Queue jobs may be automatically removed using bounded age or count policies, but removal must never erase business outcomes.

## Backpressure

Do not enqueue all campaign recipients into Redis without a bound.

Introduce a configurable queue backlog limit.

The dispatcher must pause adding delivery jobs when the number of waiting, active, delayed, and retryable jobs reaches the configured backlog threshold.

It may resume when the backlog falls below the threshold.

The durable unqueued workload remains represented by `CampaignRecipient` records in PostgreSQL.

Required configurable values include:

* preparation batch size;
* delivery enqueue batch size;
* maximum buffered queue jobs;
* worker process count;
* BullMQ worker concurrency;
* BullMQ global rate limit;
* maximum delivery attempts;
* retry backoff;
* SMTP pool maximum connections;
* SMTP pool maximum messages per connection.

Defaults must be conservative and documented as starting values rather than trusted performance values.

## SMTP Transport

Use one long-lived Nodemailer pooled SMTP transport per worker process.

Configure through environment variables:

* SMTP host;
* SMTP port;
* secure mode;
* optional username and password;
* pool enabled;
* maximum connections;
* maximum messages per connection;
* connection timeout;
* greeting timeout;
* socket timeout.

The default local target is the Mailpit Compose service on SMTP port `1025`. configurable via env

Do not use `localhost` as the default SMTP hostname from inside the API container. Use the Compose service name, such as `mailpit`. configurable via env

Close pooled transports during graceful application shutdown.

Coordinate BullMQ worker concurrency with SMTP pool capacity so that a large number of BullMQ jobs do not merely accumulate inside Nodemailer's internal connection queue.

## Delivery Processing

Each delivery job processes exactly one `CampaignRecipient`.

Before SMTP submission, the worker must atomically verify that the recipient:

* belongs to the expected campaign;
* was accepted for delivery;
* is not already terminal;
* is eligible for the next attempt.

Create a `DeliveryAttempt` record before initiating SMTP communication.

Personalize the message body using the snapshotted name and the specification-defined `Customer` fallback.

Outcome classification must preserve the specification:

* malformed or duplicate recipient: `REJECTED`, never queued;
* confirmed SMTP acceptance: `SENT`;
* definitive SMTP rejection or exhausted retryable failure: `FAILED`;
* uncertain SMTP acceptance: `DELIVERY_UNKNOWN`.

Only failures known to have occurred before SMTP acceptance may be retried.

Definitive non-retryable SMTP errors must be recorded as `FAILED` without consuming unnecessary retries.

Errors where SMTP acceptance may have occurred must be recorded as `DELIVERY_UNKNOWN` and must not be automatically retried.

A failure for one recipient must not stop processing unrelated jobs.

When BullMQ retry attempts are exhausted, persisted recipient state must be reconciled to a terminal outcome. A recipient must not remain pending merely because its queue job entered BullMQ's failed set.

## Campaign Completion and Progress

Campaign progress must be computed from PostgreSQL, not Redis and not Bull Board.

Provide APIs equivalent to:

* `POST /api/campaigns`
* `GET /api/campaigns/active`
* `GET /api/campaigns/:id/progress`
* `GET /health`
* `GET /ready`

The exact URL structure may be adjusted while preserving these capabilities.

The progress response must include every field required by the feature specification, including rejected and failed counts grouped by reason.

Campaign counters may be maintained incrementally for performance, but they must be reproducible from `CampaignRecipient` rows.

Provide a reconciliation query or service that verifies:

`total = pending + rejected + sent + failed + deliveryUnknown`

A campaign may become terminal only when:

* preparation has finished;
* no recipients remain pending;
* no accepted work remains undispatched;
* no retryable delivery work remains;
* counters reconcile.

Use atomic, conditional status transitions so multiple workers cannot complete the campaign inconsistently.

## Bull Board

Mount Bull Board at:

`/internal/queues`

Configure it in read-only mode.

Bull Board is intended for queue observability only, including:

* waiting jobs;
* active jobs;
* delayed jobs;
* retries;
* completed jobs;
* failed jobs.

It must not be used as the source for user-facing campaign progress.

Because authentication is out of scope, the Bull Board route must not be exposed as a production-public administrative interface.

## Frontend

Serve one minimal static page containing:

* subject input;
* plain-text body textarea;
* Send button;
* active campaign banner;
* progress summary;
* rejected counts grouped by reason;
* failed counts grouped by reason;
* Refresh button.

On page load, the frontend must request the current active campaign.

While an active campaign exists:

* disable or hide the subject and body controls;
* disable or hide the Send button;
* display the active-campaign banner;
* display the latest persisted progress.

The frontend is only a representation of server state. It must not enforce the single-active-campaign invariant by itself.

No frontend framework, build pipeline, WebSocket, Server-Sent Events, or automatic polling is required.

## Dummy Data

Store SQL generators under:

`/dummy`

Do not commit pre-generated recipient data.

Provide separate deterministic profiles:

* throughput dataset containing valid, unique recipients;
* validation dataset containing controlled invalid emails, missing names, blank names, and duplicate normalized addresses.

Use PostgreSQL `generate_series()` to create datasets without passing generated records through Node.js memory.

Required scale profiles:

* 1,000 recipients;
* 10,000 recipients;
* 100,000 recipients;
* 1,000,000 recipients;
* configurable values above 1,000,000.

Provide scripts to:

* clear campaign and recipient test data;
* seed a selected scale;
* seed validation fixtures;
* verify row counts;
* verify duplicate and invalid fixture counts.

Do not mix deliberately malformed recipients into the standard throughput benchmark unless the test explicitly measures validation behavior.

## Mailpit Configuration

Run Mailpit as the default dry-run SMTP service.

Configure explicitly:

* SMTP port;
* web/API port;
* message retention limit;
* temporary or persistent database path;
* storage volume when persistence is enabled.

The benchmark report must record Mailpit retention and storage settings.

Large-scale throughput results represent the complete local pipeline, including Mailpit's SMTP ingestion and storage behavior. They must not be presented as expected throughput for a production email provider.

When Mailpit message pruning is enabled, campaign correctness remains based on PostgreSQL records. Smaller correctness tests may use Mailpit's API to verify message content, personalization, recipient addresses, and duplicate behavior.

## Container Orchestration

Provide one Compose Specification file named:

`compose.yaml`

Include services for:

* PostgreSQL;
* Redis;
* Mailpit;
* NestJS API and workers.

The API and worker may run in one service for minimum scope, provided worker lifecycle and graceful shutdown remain explicit. Separate API and worker services may be used only when justified in the generated plan.

Use named volumes where persistence is required.

Include health checks for PostgreSQL, Redis, Mailpit, and the application.

Do not rely only on container startup order. The application must retry initial database and Redis connections with bounded backoff.

Avoid Docker-engine-specific features where a Compose Specification equivalent exists.

The same repository and Compose file must be validated with:

* `docker compose config`
* `docker compose up`
* `podman compose config`
* `podman compose up`

Any provider-specific limitation must be documented rather than hidden behind separate undeclared Compose files.

## Testing Strategy

Use unit tests for:

* email normalization;
* syntax validation;
* placeholder replacement;
* failure classification;
* status-transition rules;
* progress reconciliation.

Use integration tests with real PostgreSQL, Redis, BullMQ, Nodemailer, and Mailpit for:

* campaign submission;
* concurrent campaign submission;
* recipient snapshot preparation;
* duplicate detection;
* invalid-address rejection;
* successful SMTP delivery;
* definitive SMTP failure;
* retryable pre-acceptance failure;
* uncertain SMTP outcome;
* worker interruption;
* API interruption;
* Redis restart;
* queue reconstruction;
* terminal-recipient duplicate job execution;
* counter reconciliation;
* campaign completion.

Test interruption boundaries including:

* database commit before queue insertion;
* queue insertion before database enqueue-state update;
* delivery attempt creation before SMTP submission;
* SMTP acceptance before terminal database update.

Validate scale incrementally:

1. 1,000 recipients;
2. 10,000 recipients;
3. 100,000 recipients;
4. 1,000,000 recipients;
5. more than 1,000,000 recipients only after the million-recipient run passes.

Each benchmark must record:

* recipient count;
* valid, invalid, and duplicate counts;
* subject and body size;
* preparation batch size;
* enqueue batch size;
* maximum queue backlog;
* worker process count;
* worker concurrency;
* SMTP maximum connections;
* BullMQ rate-limit settings;
* retry settings;
* PostgreSQL, Redis, Mailpit, and application resource limits;
* duration;
* delivery throughput;
* preparation throughput;
* outcome counts;
* duplicate-send count;
* delivery-unknown count;
* CPU, memory, disk, PostgreSQL, and Redis observations.

Concurrency, batch size, queue backlog, SMTP-pool settings, and rate limits are trusted only after being observed at each scale.

A larger run must not begin while a smaller run has unresolved correctness, reconciliation, duplicate-delivery, or recovery defects.
